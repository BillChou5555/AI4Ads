# Android 代码开发规范

## 1. 通用原则

### 1.1 编码前先思考
- 明确说明你的假设。如果不确定，先询问。
- 如果存在多种实现方式，列出并对比，选择最简单的一种。
- 不进行推测性编码，不做需求之外的"提前设计"。

### 1.2 简单至上
- 用最少的代码解决问题，能 50 行搞定的不写 200 行。
- 不为仅使用一次的代码做抽象。
- 不为不可能发生的场景编写错误处理。
- 不提供未经要求的"灵活性"和"可扩展性"。

### 1.3 精准修改
- 只改必须修改的部分，不顺手"优化"无关代码。
- 不重构没有问题的代码。
- 遵循已有的代码风格，即使你有不同偏好。
- 发现死代码时指出，但不要直接删除。

### 1.4 目标驱动
- 将任务转化为可验证的目标：添加功能 → 先写清楚验收标准，实现后验证。
- 每个模块完成后确认功能正确再进入下一个。

## 2. 语言与注释

### 2.1 语言规范
- **代码标识符**（类名、方法名、变量名）：英文，驼峰命名。
- **注释与文档**：中文。
- **Git 提交信息**：中文。

### 2.2 注释原则
- 注释解释 **WHY**（为什么这样做），而不是 WHAT（做了什么）。
- 好的命名本身就是注释，能通过命名说清楚的不要加注释。
- 只有以下情况必须写注释：
  - 隐藏的约束条件或边界情况。
  - 不易察觉的副作用。
  - 针对特定 Bug 的 workaround。
  - 行为可能让读者感到意外的代码。
- 不写冗余注释（如 `// 设置标题` 对应 `setTitle()`）。
- 不写"作者、日期、变更记录"等版本控制已覆盖的信息。

### 2.3 注释示例

```kotlin
// 好的注释 — 解释 WHY
// 使用 postDelayed 而非直接执行，避免在 RecyclerView 布局完成前获取宽高返回 0
handler.postDelayed({ doMeasure() }, 100)

// 不好的注释 — 重复 WHAT
// 延迟 100ms 执行测量
handler.postDelayed({ doMeasure() }, 100)
```

## 3. Kotlin 编码规范

### 3.1 命名

| 类型 | 规则 | 示例 |
|------|------|------|
| 类/接口 | UpperCamelCase | `FeedAdapter`, `PlayerPool` |
| 函数/方法 | lowerCamelCase | `loadFeed()`, `onTagClicked()` |
| 变量/参数 | lowerCamelCase | `adList`, `currentTab` |
| 常量 | UPPER_SNAKE_CASE | `MAX_PLAYER_COUNT` |
| 包名 | 全小写，点分隔 | `com.aiads.ui.feed` |

### 3.2 类与方法

- 单个方法的行数不超过 40 行，超过则考虑拆分。
- 单个类的行数不超过 400 行，超过则考虑拆模块。
- 优先使用 `val` 而非 `var`。
- 优先使用不可变集合（`List` 而非 `MutableList`）。
- 避免使用 `!!` 强制非空断言，使用 `?.`、`?:` 或 `requireNotNull`。

### 3.3 协程

- ViewModel 中使用 `viewModelScope.launch`。
- Fragment 中使用 `lifecycleScope.launch` 处理 UI 相关协程。
- 数据层使用 `suspend` 函数，协程上下文由调用方决定。
- Flow 在 ViewModel 中使用 `stateIn(scope, SharingStarted.WhileSubscribed(5000), initialValue)` 转换为 StateFlow。

```kotlin
// ViewModel 中的标准 Flow 用法
private val _uiState = MutableStateFlow<FeedUiState>(FeedUiState.Loading)
val uiState: StateFlow<FeedUiState> = _uiState.asStateFlow()
```

### 3.4 密封类

UI 状态使用 `sealed class` / `sealed interface` 建模：

```kotlin
sealed class FeedUiState {
    object Loading : FeedUiState()
    data class Success(val items: List<Ad>) : FeedUiState()
    data class Error(val message: String) : FeedUiState()
}
```

### 3.5 数据类

数据模型使用 `data class`，字段名对齐服务端 JSON（snake_case → 通过 Gson `@SerializedName` 映射）：

```kotlin
data class Ad(
    @SerializedName("ad_id")
    val adId: String,
    @SerializedName("ai_summary")
    val aiSummary: String,
    @SerializedName("ai_tags")
    val aiTags: List<AdTag>
)
```

## 4. Android XML 规范

### 4.1 布局文件命名

| 类型 | 命名格式 | 示例 |
|------|----------|------|
| Activity | `activity_*.xml` | `activity_main.xml` |
| Fragment | `fragment_*.xml` | `fragment_feed.xml` |
| 列表 Item | `item_*.xml` | `item_ad_card_large.xml` |
| 通用组件 | `view_*.xml` | `view_filter_bar.xml` |

### 4.2 ID 命名

使用 `camelCase`，前缀表明控件类型：

| 控件 | 前缀 | 示例 |
|------|------|------|
| TextView | `tv` | `tvTitle`, `tvAiSummary` |
| ImageView | `iv` | `ivCover`, `ivAvatar` |
| Button | `btn` | `btnLike`, `btnClear` |
| RecyclerView | `rv` | `rvFeed` |
| ViewPager2 | `vp` | `vpMedia` |
| ChipGroup | `cg` | `cgTags` |
| EditText | `et` | `etSearch` |
| ViewGroup | `layout` | `layoutRoot`, `layoutFilterBar` |

### 4.3 资源命名

| 资源类型 | 命名格式 | 示例 |
|------|----------|------|
| 图标 | `ic_*` | `ic_search`, `ic_like_filled` |
| 背景 | `bg_*` | `bg_card_rounded` |
| 颜色 | 语义化命名 | `color_primary`, `text_secondary` |
| 字符串 | 语义化命名 | `tab_featured`, `hint_search` |

### 4.4 布局原则

- 根布局使用 `merge` 或 `ConstraintLayout`，避免过深的嵌套层级（不超过 3 层）。
- `dp` 用于尺寸、`sp` 用于字体。
- 颜色和尺寸不硬编码在布局中，统一引用 `values/colors.xml` 和 `dimens.xml`。

## 5. MVVM 架构规范

### 5.1 层次职责

| 层次 | 职责 | 不应做的事情 |
|------|------|-------------|
| Fragment/Activity | 渲染 UI、监听用户交互、向 ViewModel 发送事件 | 执行业务逻辑、直接访问网络或数据库 |
| ViewModel | 持有 UI 状态、处理业务逻辑、调用 Repository | 持有 Context/View 引用 |
| Repository | 协调数据源（Remote + Local）、缓存策略 | 持有 UI 相关对象 |
| Data Source | 执行具体的网络请求或数据库操作 | 处理业务逻辑 |

### 5.2 Fragment 模板

```kotlin
@AndroidEntryPoint
class FeedFragment : Fragment() {

    private var _binding: FragmentFeedBinding? = null
    private val binding get() = _binding!!

    private val viewModel: FeedViewModel by viewModels()

    override fun onCreateView(
        inflater: LayoutInflater, container: ViewGroup?, savedInstanceState: Bundle?
    ): View {
        _binding = FragmentFeedBinding.inflate(inflater, container, false)
        return binding.root
    }

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        initViews()
        observeState()
    }

    private fun initViews() {
        // 设置 RecyclerView、Adapter、监听器等
    }

    private fun observeState() {
        viewModel.uiState.observe(viewLifecycleOwner) { state ->
            when (state) {
                is FeedUiState.Loading -> showLoading()
                is FeedUiState.Success -> showItems(state.items)
                is FeedUiState.Error -> showError(state.message)
            }
        }
    }

    override fun onDestroyView() {
        super.onDestroyView()
        _binding = null
    }
}
```

### 5.3 ViewModel 模板

```kotlin
@HiltViewModel
class FeedViewModel @Inject constructor(
    private val repository: FeedRepository
) : ViewModel() {

    private val _uiState = MutableStateFlow<FeedUiState>(FeedUiState.Loading)
    val uiState: StateFlow<FeedUiState> = _uiState.asStateFlow()

    fun loadFeed(tab: String) {
        viewModelScope.launch {
            _uiState.value = FeedUiState.Loading
            try {
                val result = repository.getFeed(tab)
                _uiState.value = FeedUiState.Success(result.items)
            } catch (e: Exception) {
                _uiState.value = FeedUiState.Error(e.message ?: "加载失败")
            }
        }
    }
}
```

## 6. 错误处理

### 6.1 原则

- 只在系统边界处理错误（网络请求、数据库操作）。
- 内部逻辑不处理不可能发生的异常。
- 错误信息对用户友好，不暴露技术细节。

### 6.2 网络错误

```kotlin
try {
    val result = repository.getFeed(tab)
    // 处理成功
} catch (e: IOException) {
    // 网络错误 → "网络连接失败，请检查网络设置"
} catch (e: HttpException) {
    // 服务端错误 → "服务器繁忙，请稍后重试"
}
```

### 6.3 降级策略

- 网络失败时保留已有数据，不清空列表。
- 图片下载失败时显示占位图。
- 搜索/Feed 请求失败时，SnackBar 提示，不跳转错误页面。

## 7. Git 提交规范

### 7.1 提交信息格式

```
<类型>: <简短描述>

<详细说明（可选）>
```

### 7.2 类型

| 类型 | 使用场景 |
|------|----------|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `refactor` | 重构（不改变功能） |
| `style` | 格式调整（不影响代码逻辑） |
| `docs` | 文档更新 |
| `chore` | 构建、依赖等杂项 |

### 7.3 示例

```
feat: 实现 Feed 信息流列表渲染

- RecyclerView + ConcatAdapter 支持多态卡片
- 接入服务端 cursor 分页
- 下拉刷新与上拉加载更多
```

### 7.4 规则

- 一个提交只做一件事。
- 提交信息描述 **做了什么** 和 **为什么**，不描述怎么做的。
- 不提交调试代码、注释掉的代码、临时文件。

## 8. 依赖与第三方库

### 8.1 版本管理

- 所有依赖版本统一定义在 `gradle/libs.versions.toml`（Version Catalog）中。
- 不直接在模块 `build.gradle.kts` 中硬编码版本号。

### 8.2 引入原则

- 优先使用项目已有库，不引入功能重叠的新库。
- 引入新库前确认：是否必要、是否有维护、是否与现有库冲突。
- 不使用已停止维护的库。

---

## 9. 代码审查 Checklist

每个 MR/PR 提交前自查：

- [ ] 代码风格符合本规范。
- [ ] 无硬编码字符串/颜色/尺寸（已在 XML 资源中定义）。
- [ ] 无 `!!` 非空断言（或已确认不可避免）。
- [ ] ViewModel 不持有 Context/View 引用。
- [ ] Fragment 中 `binding` 在 `onDestroyView` 中置 null。
- [ ] 网络请求有错误处理。
- [ ] 无调试代码、注释代码、临时日志。
- [ ] 功能已验证通过。
